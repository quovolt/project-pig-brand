# B3 · 一餐怎么被准备好

最早的[「生活主理人」企划](./../../life-curator-plan)是从一个两难出发的：上班前买肉，不好保存；下班再买，又未必挑得到想要的部位。即使买到了，议价、看优惠、算什么时候下单，又占去一段本来可以用来过日子的时间。B1 后来才把这层意思讲透：品牌帮人把准备做可靠，至于这顿饭怎么安排、是否改主意，仍是人的决定。

## 提前预约和临时起意，不走同一条路

原案给了两条路径。**提前预约**，人先提出部位、数量和时间，再按订单匹配产线、分割和配送；自有供给所掌握的来源、分割与订单信息，可以作为建设溯源的基础。**临时采购**用市场调配或补货响应计划之外的需求，掌握的信息与自有链不同，不能把原有溯源说法平移过去。企划里的「不设库存」指线上不为未产生的订单预留待售肉品；预约无法履约后拟转线下销售，是另一段交接，不是顾客获得了无条件取消或改送的权利。

定价原则同样出自这层分工：**同一天内挂牌价固定**，不把日内采购成本波动转给正在选购的人；减少以凑单、算券换取价格的负担。跨日、促销例外和具体口径还要定义；日内挂牌原则不等于跨日价保。临时采购也没有推出两小时送到或每次都能调整的承诺。

## 顾客眼前的一步，后台要对得上

原案用「聆听、记录、适时提供」概括小程序。人可以记下喜欢的食材和想做的菜，必要时找到烹饪准备建议，也可以只买一份肉。要检验这段关系，先不把整份企划做进原型。挑一个高代价的时刻：**选好的时段突然满了，人在付款前要知道这单还订不订得成。**

这里的关键不是把「抱歉」写得温柔。当时段刚满，原型应该试着保留已填信息，只给真实可选的替代；若备选改变肉品日期或总价，先把差异摆出来，再让人选。后台则要分清库存与配送有没有位置、是否已经发起付款、订单是否确认。付款状态未知，页面就不能说「未扣款」。这是根据企划整理的验收用例，不是已上线流程。

还有三件事不能拿这个例子代过：

- **同款同日怎么看价格。** 用同一规格、商品状态和标示肉品日期做对照，分别呈现肉品日期与配送时段；两次下单看到的挂牌基价按什么口径比较，要先同运营核实。
- **已经确认后还能不能改。** 要单独核对原时段和备选时段，用户同意之前与之后各是什么状态；若中断或重复提交，回来还能读到同一个明确结果。无法保留新时段时，改约界面不能继续说它已经可用。
- **两条供给路径怎么说明。** 临时外采进入订单，和已安排的肉品转线下，是方向相反的两次交接。每次都要说清来源、去向和责任，再决定标签或订单页能展示什么。资质、食品安全与运营条件还需核验。

B3 的第一份交付应是一处真实触点连同背后的规则：界面上说什么，谁能做、哪种情况下能做，正常、变化和异常时顾客能不能判断下一步。先从数字订单和肉品标签中验证真的要用的载体，不为凑齐品牌系统另造线下场景。目前有原企划和验收用例，尚没有完整服务的验收结果。若发现后台做不到，就改对应规则和告知，重跑受影响的分支；只有当能力本身动摇了「让变化得到回应」，才回到 B1 讨论这条价值还怎么成立。
